# Module signing: why modules must be signed by hand

This document explains the one thing that breaks most attempts to ship
out-of-tree modules (rtl8812au, WireGuard, rtl8188eu and friends) for NetHunter
kernels: **module signature enforcement**. If you ever saw an `insmod` fail
with `Key was rejected by service` or `Required key not available`, this is
that story, and this template's answer to it.

## The three config options that cause it

NetHunter kernels (this template's kernels included) are built with:

    CONFIG_MODULES=y
    CONFIG_MODULE_SIG=y
    CONFIG_MODULE_SIG_FORCE=y
    CONFIG_MODULE_SIG_SHA512=y

`CONFIG_MODULE_SIG_FORCE=y` means the kernel refuses to load any module whose
signature it cannot verify. There is no override at runtime, no `enforce=0`
boot flag that helps once the kernel is this way, and no way to disable it
from userspace. A module either carries a signature made with the key embedded
in that kernel image, or it never loads.

## Why the kernel does not sign modules automatically

The kernel *can* sign modules automatically. That is what
`CONFIG_MODULE_SIG_ALL=y` does: during `make modules_install`, kbuild runs
`scripts/sign-file` on every module it installs. The catch is that Android
kernel distribution does not use `modules_install`.

Flashable zips (AnyKernel3 and similar) deliver raw `.ko` files that get copied
into `/system/lib/modules` or a systemless overlay at flash time. Nothing in
that path runs kbuild, so nothing signs anything. The result is a kernel that
enforces signatures and a set of modules that were never signed: the modules
in the official Kali builder output, in most prebuilt module repos, and in
almost every forum attachment simply do not load on a SIG_FORCE kernel.

## How this template does it

The signing key is generated by the kernel build itself. Because
`CONFIG_MODULE_SIG_ALL=y` (needed for the tooling) plus `CONFIG_MODULE_SIG_FORCE=y`
are set, `make` creates an ephemeral key pair under the build output:

    out/certs/signing_key.pem
    out/certs/signing_key.x509

The x509 certificate is compiled into the kernel image. The private key stays
in the build directory. After each module build, `lib/sign-module.sh` runs the
kernel's own `scripts/sign-file`:

    out/scripts/sign-file sha512 \
      out/certs/signing_key.pem \
      out/certs/signing_key.x509 \
      88XXau.ko

and then verifies the signature is really there:

    tail -c 4096 88XXau.ko | grep -aq "Module signature appended"

That verification is not cosmetic. `sign-file` appends the signature at the
end of the file; if the key was missing or the file got rewritten afterwards,
the module would look fine and still fail on device. The template treats a
missing signature as a build failure, not a warning.

## The consequence nobody tells you: key per build

The signing key exists only inside one CI run. A module signed in yesterday's
build will not load in today's kernel, and vice versa. That is why this
template never ships modules separately from the kernel they were built
against: the kernel and its modules are produced, signed, packaged and
released in the same run. The `modkit` workflow (module.yml) also builds the
kernel first, for the same reason, and because `CONFIG_MODVERSIONS=y` kernels
need the `Module.symvers` file from a full build before any out-of-tree module
can link.

The practical takeaway if you build modules elsewhere: keep kernel and modules
from the same release, or rebuild both. A flashable zip from this template
already satisfies this by construction.

## Verifying on device

After flashing, check that modules load cleanly:

    dmesg | grep -i module
    insmod /system/lib/modules/88XXau.ko && lsmod

On a properly signed module there is no taint warning about unsigned module
load. If you build your own module against this template's kernel sources and
want to sign it, you need the private key from the same run, which is why
forking the template and adding your module under `modules/` is the supported
path rather than signing by hand later.
